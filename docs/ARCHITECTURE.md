# ARCHITECTURE

## Структура

```text
video_downloader.py       # запуск
src/
  application.py          # композиция mixin + короткая оркестрация старта
  bootstrap.py            # main/crash startup
  app/                    # пути и mutable-state инициализации
  core/                   # общие runtime-механизмы
  downloads/              # URL, yt-dlp, 1080p, очередь, media validation
  audio/                  # convert / merge / split
  ui/                     # Tkinter UI по зонам ответственности
  diagnostics/            # problem logs, retention, schema, incidents, validator
docs/                     # документация
Настройки/                 # пользовательские настройки
```

## Как искать нужный код

1. UI-проблема → `src/ui/`.
2. Не скачивает / плохое качество / yt-dlp → `src/downloads/`; workflow — `youtube_downloader.py`, каталог fallback — `youtube_strategy_catalog.py`, CLI args — `youtube_command.py`.
3. subprocess зависает / отмена → `src/core/subprocess_runner.py`, `process_control.py`, `ytdlp_runtime.py`.
4. Конвертация/склейка/разрезание аудио → `src/audio/`.
5. Логи проблем → `src/diagnostics/`.
6. Настройки → `src/core/settings.py`; пути/папки → `src/app/paths.py`; runtime-state → `src/app/state.py`.

## 1080p contract

- Программа не должна выбирать видео выше 1080p.
- Если 1080p доступно, high-quality video+audio стратегии должны получить приоритет перед progressive 720p/360p.
- Результат ниже 1080p от high-quality стратегии — резерв, а не немедленный успех.
- После исчерпания high-quality путей допустим лучший реально доступный вариант ниже 1080p.
- Фактическое разрешение определяется через ffprobe, а не по имени формата yt-dlp.

## Почему много небольших файлов

Разделение сделано по owner-логике: каждый файл отвечает за одну понятную область. Это позволяет ChatGPT/Codex сначала читать 1–3 релевантных файла вместо нескольких тысяч строк монолита.

Token-efficient границы отделяют orchestration от деталей: `youtube_downloader.py` держит control flow, `youtube_attempt.py` — setup/context, `youtube_retry.py` — классификацию ошибок, `youtube_success.py` — обработку успешного результата, `youtube_finalize.py` — финальный fallback/reporting, `youtube_strategy_catalog.py` — каталог стратегий, `youtube_command.py` — CLI. Инициализация путей/state вынесена из `application.py` в `src/app/`.
Большие diagnostic utility-модули также разделены: `validator.py` и `retention.py` оставлены короткими фасадами, а core/integrity/session и base/archive/storage детали вынесены в отдельные owner-файлы.


## Выбор качества и выполнение

- Селектор ограничивает высоту 1080; сначала выбирается высота, затем доступный битрейт видео и аудио. Предпочтение расширения не понижает разрешение. Раздельные потоки объединяются в MKV без перекодирования.
- Progressive остаётся резервом; недоступность форматов/сети может ограничить достигнутое качество. Битрейты разных кодеков не являются прямой мерой визуального качества.
- Настройки фоновой сессии фиксируются на главном потоке перед запуском worker; изменения UI действуют со следующей сессии.
- Проверка MP3 отклоняет неизвестную длительность и отклонения в обе стороны от допуска из `src/core/constants.py`. Проверка длительности не доказывает идентичность содержимого.
- Проверки: `python -m unittest discover -s tests`; импорт `src.application` не запускает GUI. Конструктор приложения создаёт состояние относительно корня проекта, поэтому для проверок используйте изолированную копию без пользовательских данных.
- Ручная проверка: скачать короткое видео с доступным 1080p, проверить разрешение и начало/конец MP3; затем отменить следующую загрузку и начать новую с изменёнными настройками.

При ошибке публикации `.preserve_download` защищает папку результата от очистки следующей сессией. Каждый запуск получает отдельную временную папку. Защищённые результаты сохраняются для ручного восстановления; автоматического срока удаления у них нет.

## Завершение очереди

Менеджер считывает результаты фоновых задач. Необработанные ошибки привязываются к ссылке и попадают в список неудачных загрузок. Завершение вызывается через `finally`, в том числе после ошибки создания папки или конвертации. `download_outcome` различает `completed`, `failed`, `cancelled`; интерфейс различает отмену, неудачные загрузки и исключения, дошедшие до менеджера. Ошибки и отмена объединения/разбиения аудио передаются менеджеру. Повторный запуск во время активной сессии игнорируется.


## Безопасность аудиорезультатов

Конвертация не использует существующий MP3 только по совпадению имени и длительности: создаётся новый файл со свободным именем. Старые файлы сохраняются.

Объединение требует наличия всех указанных входов и конечных положительных длительностей. Merge и split выполняются в отдельных `.merge_*`/`.split_*` папках внутри «Разбивка аудио». При сбое рабочая папка сохраняется для ручного восстановления; автоматической очистки таких материалов нет. Split не удаляет исходник; merge удаляет свой промежуточный MP3 только после успешного сохранения частей.

Перед сохранением проверяются результат FFmpeg, наличие частей и расхождение общей длительности менее допуска из `src/core/constants.py`. Разбиение не создаёт границу в последние 0,1 секунды: короткий хвост остаётся в последней части. Старые итоги не перезаписываются. При отказе переноса частей выполняется возврат уже перенесённых частей в рабочую папку. Если файловая система блокирует и возврат, оставшийся путь явно записывается в диагностику; исходник сохраняется, операция не объявляется успешной.

Реальная локальная проверка использует разные звуковые тоны и проверяет их порядок после объединения/разбиения. Проверка длительности произвольного пользовательского материала не доказывает идентичность всех сэмплов. Ручной тест: два коротких видео → MP3 → объединение, затем отмена и повторный запуск; проверить, что прежние MP3 сохранены и итоговый статус соответствует результату.
